# Reconnaissance for the Winelib port (native ELF)

Original date: 2026-08-09 . Branch `main` @ `ac5472e`. Updated the same day after
completing Phase 0 of the plan.

Every claim in this document is backed by commands run on this machine. The
reconnaissance experiments were done in a temporary directory outside the
repository; the Phase 0 changes (`src/cmake/`, `src/CMakeLists.txt:79-89`) are
in the tree and are detailed in the "Phase 0, executed on 2026-08-09" section
below.

## 0. Executive summary

The port is **more viable than `CMakeLists.txt` suggests**. With three compiler
flags (`-std=gnu89 -funsigned-char -fms-extensions -fpermissive`), a case
compatibility directory for 12 headers, and the headers generated by
Microsoft's tools, **156 of the 207 translation units of the engine
(`opus_original_engine`) compile without touching a single line of
`src/Opus/`** (186 remaining errors, spread across 51 files). The original
reconnaissance figure was 154/207 with 202 errors; Phase 0 added two modules
(`menuhelp.c`, `eldlg.c`) when it resolved item 2.

The five real obstacles, in order of risk:

| # | Obstacle | Status |
|---|---|---|
| 1 | 427 Word commands are resolved via `GetProcAddress` against the export table of the executable itself, generated by `#pragma comment(linker,"/export:")` | **Resolved in principle**: verified that a winebuild `.spec` exposes symbols via `GetProcAddress` in a Winelib ELF |
| 2 | `src/cmake/` did not exist in any commit; the build referenced two missing files | **Resolved in Phase 0** (`src/cmake/GenerateMenuHelpHeader.cmake`, `src/cmake/GenerateElxInfoHeader.cmake`). No longer a blocker. |
| 3 | Case-sensitive filesystem: 12 headers, 202 affected files | Mechanical |
| 4 | `long` is 8 bytes on Linux LP64 and 4 bytes on Windows LLP64 | Bounded, but requires auditing |
| 5 | libstdc++ is unusable for wide strings under winegcc's `-fshort-wchar` | Bounded to ~5 files, all in `src/port/` |

### 1.6 Pre-ANSI C constructs that GCC rejects

This is the inventory the assignment did not explicitly ask for but that
dominates the real effort. Figures obtained by compiling the 207 engine TUs
with winegcc (see §6 for methodology):

| Error class | Occurrences | Files |
|---|---:|---|
| *cast as lvalue*, `*((int *)p)++` | 21 | `Opus/style.c` (6), `Opus/ffread.c` (3), `Opus/interp/exp.c` (2), `OpusEtAl/tools/src/mkcmd.c` (5), + 5 in assignment variants |

| K&R definition conflicting with ANSI prototype | 13 | `Opus/help.h:229` vs `port/original/about.sdm:5`, `Opus/help.c:316`, etc. |
| `static` after a non-`static` declaration | 10 | scattered |
| Call with more arguments than an empty K&R prototype | 9 | function pointers declared `()` |
| Nested `struct` with a tag and no member name (MS extension) | ~0 after `-fms-extensions` | `Opus/wordtech/props.h:229` (`struct PAP` / `struct PAPS`), **resolved with `-fms-extensions`** |

Important note: `struct PAP` contains `struct PAPS { ... };` with no member

GCC. Before adding the flag, that single pattern made `search.c`, `layout.c`,
`layout1.c`, `layout2.c`, and others fail; afterward it disappears completely.

### 1.7 The architectural dependency: executable exports

`port/original/opus_asm_movecmds.c:174-177`:

```c
HMODULE module = GetModuleHandleW(NULL);
return (OPUS_PFN)(uintptr_t)GetProcAddress(module, name);
```

Word resolves **every command** by name against the export table of its own
executable. That table is populated by `opuscmd_native.inc`, generated by
MKCMD, with one `#pragma comment(linker, "/export:NAME")` line per function.

I ran MKCMD on Linux (§3) and counted: **427 exports, 427 unique names.**

GCC ignores `#pragma comment` with a warning, so compilation *would* pass and
the binary would fail at runtime when resolving the first command. Under
Winelib the equivalent is a winebuild `.spec` file.

**Experimentally verified** (`exp.c` + `exp.spec` -> `winegcc -o exp.exe exp.c exp.spec`):

```
module=0x7f5812880000 CmdHelp=0x7f581289042e -> 4242  CmdFoo=0x7f5812890439
```

`GetProcAddress(GetModuleHandleW(NULL), "CmdHelp")` resolves correctly in a
Winelib ELF when the symbol is declared in the `.spec`. **The riskiest
assumption of the port is validated.**

### A POSIX convention problem in BITAPP

`OpusEtAl/tools/src/bitapp.c:59`:

```c
if (*(rgszArg[cCurArg]) == '/')
    SetFlag(*(rgszArg[cCurArg]+1));
```

Any argument starting with `/` is interpreted as a DOS-style switch. Since
CMake passes absolute paths, **every BITAPP invocation fails on Linux** with
`Invalid Switch on command line.` The fix does not require touching
`bitapp.c`: it is enough to invoke it with relative paths from a
`WORKING_DIRECTORY`. Verified: with `./mk/bitapp res/8hdr.bmp gen/8hdr.hb`
argument parsing already passes.

A secondary undiagnosed failure remains (`Unexpected End Of File Reached in
Input file!`) that is almost certainly §4.1: `bitapp.h:29` declares `typedef
unsigned long DWORD;`, so `sizeof(struct BITMAP)` changes on LP64 and
`fread(&bm, sizeof(BITMAP), 1, ...)` reads the wrong number of bytes. It is the
cleanest evidence that the `long` problem is real and not theoretical.

entries. No files are missing in that part.

### 3.3 What `wrc` can assume

**`wrc` compiles `port/word1.rc` as is, with no modifications.** Verified:

```
$ wrc -I src/port -o word1.res src/port/word1.rc
FYI: Starting parse
FYI: Writing .res-file      -> 28140 bytes
```

It handles `#include <windows.h>`, `RT_MANIFEST`, `VS_VERSION_INFO`, and

1. **`winegcc` rejects `.rc` files on its command line**:

   `No CMAKE_RC_COMPILER could be found.` The Ninja preset must declare only
   `C CXX` and handle `wrc` with `add_custom_command`.

## 4. LP64 vs LLP64 assumptions embedded in the code

This is the point that does not appear in any inventory of "MSVC constructs"
and yet has the widest reach.

### 4.1 `long` changes size

```
$ winegcc -o sz.exe sz.c && ./sz.exe
long=8 LONG=4 DWORD=4 ptr=8 int=4 wchar_t=2
```

Wine does the right thing: `LONG` and `DWORD` are 4 bytes. But **bare `long`
is 8 bytes**, against 4 under MSVC x64. In the compiled tree there are **1254
occurrences of `long`, spread across 206 files**. The hotspots are
`port/original/opus_asm_native_adapters.cpp` (54), `Opus/CLIPBRD2.C` (37),
`Opus/wordtech/plc.c` (29), `Opus/wordtech/savefast.c` (25),
`Opus/wordtech/file.h` (25).

Worse: two headers redefine Windows types with their own `long`:

- `Opus/lib/qwindows.h:119`, `typedef unsigned long DWORD;`
- `OpusEtAl/tools/src/bitapp.h:29`, `typedef unsigned long DWORD;`

`qwindows.h` **is** reachable from the engine: `Opus/interp/sym.c:6` does
`#include <qwindows.h>` and `sym.c` is in the source list.

Not all 1254 occurrences are dangerous, many are local counting variables.
The ones that matter are the ones that appear in structs serialized to Word's
file format, in the PLC tables, and in `sizeof` calculations. It requires
targeted auditing, not a global `sed`.

### 4.2 2-byte `wchar_t` breaks libstdc++

winegcc always passes `-fshort-wchar`. libstdc++ and glibc are built with a
4-byte `wchar_t`. The symbols link (`wchar_t` mangling does not depend on
size), so **the error is silent at link time and visible only at runtime**:

```cpp
std::wstring w = L"abc";
std::cout << w.size();     // prints 175, not 3
```

(verified by running the resulting Winelib binary)

Scope: bounded and entirely within `src/port/`. The sites that use wide
CRT/STL functions are `opus_win95_chrome.cpp` (13), `opus_word1_ui_test.cpp`
(~21), `opus_original_startup_probe.cpp` (3). Using `WCHAR`/`L""` with Wine's
`...W` APIs is correct and needs no changes.

## 5. Visual Studio generator assumptions

### 5.1 In `CMakePresets.json`

| Line | Assumption | Impact |
|---|---|---|
| `"generator": "Visual Studio 17 2022"` | Multi-configuration generator | The three presets are unusable on Linux. Ninja presets must be **added** without deleting these. |
| `"architecture": {"value":"x64","strategy":"set"}` | Only VS/Xcode accept `architecture` | Ninja ignores it or fails. |
| `"CMAKE_INTERMEDIATE_DIR_STRATEGY": "SHORT"` | VS-specific cache variable | Harmless. |
| `"binaryDir": "${sourceDir}/../out"` | -- | Portable. |
| `buildPresets` with `"configuration": "Debug"/"Release"` | Multi-configuration | Ninja presets need `CMAKE_BUILD_TYPE`. |

### 5.2 In `src/CMakeLists.txt`, hard blockers

1. **Line 5-7**, `if(NOT WIN32) message(FATAL_ERROR ...)`. Explicit block.
2. **Line 3**, `LANGUAGES ... RC`. Fails on Linux (§3.3).
3. **Lines 59-64**, `$ENV{ProgramFiles(x86)}` +
   `${CMAKE_VS_WINDOWS_TARGET_PLATFORM_VERSION}` to locate `Windows.h` from
   the Windows Kits SDK, with `FATAL_ERROR` if it does not exist.
   `CMAKE_VS_WINDOWS_TARGET_PLATFORM_VERSION` **is only defined by the VS
   generator**. It feeds `port/original/opus_windows_sdk.h.in`, whose only
   content is `#include "@OPUS_WINDOWS_SDK_HEADER@"`.
   The mechanism is sound: `port/original/windows.h` (with `#pragma once`)
   acts as a screen so `Opus/windows.h` does not shadow the modern SDK, and
   redirects to `opus_windows_sdk.h`. **For Winelib the template just needs to
   point at `/usr/include/wine/windows/windows.h`.** I verified it: with that
   substitution the include chain works (without it, a silent cycle occurs via
   `#pragma once` that leaves `HMODULE`, `BOOL`, `FARPROC` undefined).
4. **Lines 79-89**, an `add_custom_command` that invokes
   `powershell -File cmake/GenerateElxStid.ps1`.
5. **Line 349**, `-P cmake/GenerateMenuHelpHeader.cmake`.

### 5.4 Harmless assumptions

`FOLDER`, `VS_GLOBAL_VcpkgApplocalDeps`, `VS_DEBUGGER_WORKING_DIRECTORY`, and
the `RUNTIME_OUTPUT_DIRECTORY_${config_upper}` loops are properties Ninja
ignores. They require no action and must be kept so as not to break the VS

### 5.5 Two winegcc command-line traps

- **`winegcc` drops `-x`.** Verified: `winegcc -v -c -x c t0.c` does not
  propagate the flag to gcc. This matters because the engine contains **17
  sources with uppercase `.C` extension** (`CLIPBORD.C`, `CLIPBRD2.C`,
  `CREATE2.C`, `EDIT.C`, `DDESRVR.C`, `DLBENUM.C`, `FILE2.C`, `FIELDCMD.C`,
  `GRSPEC.C`, `LOADFONT.C`, `PIC2.C`, `RTFIN.C`, `RTFOUT.C`, `RTFRARE.C`,
  `SCREEN2.C`, `SYSCHG.C`, `SPELL.C`), which gcc treats as C++.
  `CMakeLists.txt:670` already marks them `LANGUAGE C` for MSVC, but that only
  selects the compiler, not the front end. Left unaddressed, those 17 TUs
  generate ~2800 errors. The workable fix is to materialize lowercase symlinks
  inside the build tree (a `src/port/` step).
- **`-mno-cygwin` (msvcrt headers) is incompatible with libstdc++.** In that
  mode `_stricmp`, `_snprintf_s`, `<direct.h>`, `<io.h>` are available, but
  `#include <string>` fails with conflicts in `<cwchar>`. Since `src/port/`
  uses the STL extensively (31 files), **the glibc default mode must be kept,
  supplying the ~6 Microsoft CRT symbols from `src/port/`.**
- **`opus_x64_compat.h:135`'s `#define native` poisons libstdc++'s `<bit>`**
  (`enum class endian { little, big, native }`). It is the sole cause of the
  failure in `opus_asm_file2.cpp`, `opus_asm_filewin.cpp`, and
  `opus_asm_misc.cpp`. The author already used the remedy in
  `port/tools/opus_cabi_tool.cpp:3` (`#undef native`). The same applies to
  `#define string` and `#define sys`.

### An unanticipated problem: `mkdlg.c` had the same `_stricmp` gap as `mkcmd.c`, under a different name

The approved plan only mentioned `_stricmp` in `mkcmd.c`. When linking
`mkdlg`, `undefined reference to 'strcmpi'` appeared: `mkdlg.c:718` calls
`strcmpi()` directly, relying on the MSVC CRT declaring it as a deprecated
alias for `_stricmp()`, which it does without the source code asking for it.
GCC has neither name. It is the same Microsoft CRT gap, under a different
spelling. Resolved with the same pattern `mkcmd.c` already used
(`#define strcmpi _stricmp`), and `opus_host_compat.h` was designed to expose
only Microsoft's real primitive (`_stricmp`), letting each file map its own
spelling onto it, which avoids two files that include the same shared header
stepping on each other's `strcmpi` macro.

### A real bug found and fixed: `bitapp.h:29`, not just diagnosed

Phase 0 had flagged `typedef unsigned long DWORD;` (`bitapp.h`, then line 29)
as suspicious but unconfirmed. When BITAPP actually ran over the 51 bitmap
resources, **46 of 51 failed** with `Unexpected End Of File Reached in Input
file!`, also producing corrupted data (not empty) before failing, a dangerous
silent regression if it had not been caught by the exit code.

Confirmed cause: `struct BITMAP` (`bitapp.h:40-51`) serializes `bmBits` as
`DWORD`, a 4-byte Win16 field the code always discards. Under MSVC x64
(LLP64), `long` is still 4 bytes and the `typedef` is exact. Under GCC x64
(LP64), `long` is 8 bytes: `sizeof(BITMAP)` went from 14 to 18 bytes, and
`fread(&bm, sizeof(BITMAP), 1, fpOrig)` read 4 extra bytes per resource,
misaligning everything that followed.

Fix: `DWORD` becomes `uint32_t` only under `OPUS_X64_TOOL` **and** non-MSVC
GCC, the MSVC x64 (Windows) build stays byte for byte unchanged, because the
bug does not exist there.

**Independent verification, without relying on BITAPP itself:** the 46
`.bmp` files were re-read with Python using `struct.unpack` directly on the
raw file bytes (`<hhhhBB` at offset 2, i.e. the real 14-byte Win16 layout),
and it was confirmed that `2 (signature) + 14 (header) + bmWidthBytes x
bmHeight` matches **exactly** the size of each of the 46 files, zero
discrepancies. This test does not use BITAPP at all; it derives the fix from
the file format documented in `DumpBitmapParameters` itself. The same was
done for the 5 figure icons/cursors (`RCI`, 12 bytes, all `short` fields, no
`DWORD`, never had the bug) and for the 7 cursors in `Opus/resource/*.cur`,
confirming that the byte consumption of `DumpFigureParameters` + two calls to
`DumpBits` (AND/XOR masks) does not exceed the file size in any of the 12
cases.

### Active blocker: `src/port/tools/opus_cabi_tool.cpp:98`

```cpp
std::ofstream output(directory / file_name, std::ios::trunc);
```

`directory` is `std::filesystem::path`. Under `wineg++`,
`std::filesystem::path::value_type` is `wchar_t` (Windows type model,
`-fshort-wchar` forced by winegcc, the same mechanism documented in §4.2 of
this report for libstdc++'s STL and wide strings). `std::basic_ofstream<char>`
has no constructor that accepts a `const wchar_t*`/`path` of that type by
implicit conversion; it fails in `<fstream>` with 5 candidate overloads
rejected, each for a different reason, confirmed by compiling the real file,
not a reduced reproduction.

It is the **only occurrence** of `std::ofstream`/`std::ifstream`/`std::fstream`
in the file (confirmed with `grep`); there are no other sites of the same
pattern to fix in the same file. There is also no existing convention
elsewhere in the tree for converting a `path` before passing it to a stream,
it is the only use of `std::filesystem` under `src/port/` with this problem,
so the simplest fix (forcing `.string()` at the call site) has no precedent
to follow or contradict.

**This is not an isolated problem of a secondary tool.** Dependency chain
confirmed with a real `ninja -C out/linux-winelib-debug opus_original_engine`
(not deduced only by reading `CMakeLists.txt`):

```
opus_cabi_tool (fails to compile)
  -> OPUS_GENERATED_CABI_OPEN (cabi/open.hs, custom command, line ~365)
    -> dependency of the rule that produces opuscmd.h (opus_generated_commands, line ~407)
      -> add_dependencies(opus_original_engine opus_generated_commands ...) (line ~726)
```

Without `opuscmd.h`, no file in `opus_original_engine` compiles, the
`opus_cabi_tool` blocker is the blocker of the whole engine, not of a
dispensable utility.

### Empirical verification of the ABI hypothesis (2026-08-09)

The starting hypothesis, that `winegcc`/`wineg++` define `_WIN32`, which
activates `_GLIBCXX_FILESYSTEM_IS_WINDOWS` in libstdc++'s headers and sets
`path::value_type = wchar_t`, while the portion of `std::filesystem` already
compiled into Fedora's `libstdc++.so` is ELF/POSIX, was put through a direct
test with three minimal binaries compiled with `wineg++ -std=c++17`, not
taken on faith. Result: **confirmed, and worse than the hypothesis alone
suggested.**

- `sizeof(fs::path::value_type)` = 2 (`wchar_t`): the header model is indeed
  Windows's.
- But `is_absolute("/tmp/x")` gives `false` and `is_absolute("C:\\x")` also
  gives `false`, with `root_name()`/`root_directory()` empty, neither
  semantics (POSIX or Windows) applies consistently. Path parsing is broken,
  not simply "assumes Windows".
- **`fs::path::operator/` (the join line 98 uses:
  `directory / file_name`) corrupts memory and hangs the process**
  (`malloc(): invalid size` followed by `stack overflow` in Wine's unwind),
  reproduced deterministically in a minimal 15-line case, unrelated to
  `std::ofstream`. Simple construction of a single-component `path` and its
  `.string()` ARE safe (independently confirmed).
- **`std::filesystem::create_directories` (line 119, no join) also corrupts
  memory and hangs the process**, with the same error signature. This is a
  second, distinct entry point, not textually the same `std::ofstream`
  pattern instruction point 4 asked to review, but the same root cause: any
  `std::filesystem` function resolved out of line in `libstdc++.so`
  (`operator/`, `create_directories`, `directory_iterator`, the three
  tested) fails under this `wineg++`/`libstdc++`. Only what resolves
  entirely in the header (construction, `.string()` of an uncomposed `path`)
  was verified safe.
- Control case that DOES work end to end, without touching any out-of-line
  `std::filesystem` symbol: construct the directory `path` only to get its
  `.string()`, concatenate with a normal `std::string`
  (`dir.string() + "/" + file_name`), and pass that `std::string` to
  `std::ofstream`/`std::ifstream`. Run and verified by reading back the
  written content, clean exit (`EXIT=0`), no corruption either during
  execution or at process shutdown.

**Consequence for the fix candidate previously noted here
(`(directory / file_name).string()`): it is ruled out.** That expression
evaluates `operator/` before `.string()`, and it is exactly `operator/` that
corrupts memory, the original candidate would have swapped the compile error
for a runtime hang, not resolved it.

### Concrete next step, before continuing anything else

The scope of the fix is wider than this instruction point's original plan
anticipated (which spoke only of line 98 and the `std::ofstream` pattern).
There are two sites in `opus_cabi_tool.cpp`, not one, and both depend on
broken out-of-line `std::filesystem` symbols:

1. Line 98 (`std::ofstream output(directory / file_name, ...)`), fixable
   with the already verified control pattern: build the path `std::string`
   with simple concatenation, without `operator/`.
2. Line 119 (`std::filesystem::create_directories(output_directory,
   error)`), needs to be replaced with directory creation that does not go
   through the broken `libstdc++.so` symbol; candidates: direct POSIX
   `mkdir()`/`_mkdir()` (`opus_cabi_tool`'s output directory has no known
   deep nesting in this tree, to be confirmed before assuming a single-level
   `mkdir` suffices) or a custom recursive function over `mkdir()`.

Both share a cause (avoid every `std::filesystem` symbol resolved out of
line). The fix ultimately applied goes beyond wrapping the conversion: it
removes `std::filesystem` from the file entirely. See the next section.

### Closing the `.string()` / `native()` discrepancy, platform rule

There was a discrepancy between audits about whether `.string()` on a
`std::filesystem::path` was safe under `wineg++`. **Resolved against
`.string()`**, by a second Grok Build audit with isolated probes and 3/3
determinism: `.string()` is deterministic heap corruption. (Kimi was ruled
out at this specific point.)

It is worth recording why the local measurement done here did not detect it,
because the failure mode is instructive: the local probe `fs_probe4` used
`dir.string()` on a single-component `path`, printed the correct value, and
exited with `EXIT=0`. But probe `fs_probe5`, with the same pattern, printed
correct results and **still aborted at process shutdown** with
`Inconsistency detected by ld.so: dl-fini.c: 93`. That is: the corruption
happens all the same, it just sometimes does not surface until after the
output already looks correct. A clean output is not evidence of absence of
corruption here. The audit with isolated probes and 3/3 repetition is the
valid measure; a single pass with `EXIT=0` is not.

`native()` survives the tests, but **is not usable in practice**: under this
toolchain it returns `wstring`/`wchar_t`, and what `WriteCabi` needs is a
`char` path for `std::ofstream`. No `std::filesystem::path` method is safe to
use for this purpose.

With four independent conversion mechanisms already confirmed broken
(`operator/`, `.string()`, `directory_iterator`, `create_directories`) and
only `native()` and simple construction surviving, neither usable here, the
following **platform rule** is recorded:

> Under `wineg++`, `std::filesystem::path` must not be used for any
> operation that produces or consumes a `char` string representation.
> Construction from `const char*` and structural comparison may be safe, but
> there is no real use case for that in this tree. **Practical rule: do not
> use `std::filesystem` in translation units compiled with `wineg++`.**

### Fix applied to `opus_cabi_tool.cpp`

Single origin located by Grok Build: the conversion of `argv[1]`
(`const char*`) to `std::filesystem::path` at L117. Once that conversion is
removed, `std::filesystem` disappears from the entire file.

- `#include <filesystem>` removed, replaced with a comment explaining the
  prohibition and pointing to the platform rule above.
- `WriteCabi` signature: `const std::filesystem::path& directory` ->
  `const std::string& directory`.
- Site ~98: `directory + "/" + file_name` with a normal `std::string`, into a
  local variable, and that variable to `std::ofstream`'s constructor. No
  `path` is constructed along the way.
- Site ~119: `create_directories` removed with no replacement. **No CMake
  change was needed**: the `add_custom_command` that invokes the tool
  (`src/CMakeLists.txt:366`) already ran
  `"${CMAKE_COMMAND}" -E make_directory "${OPUS_GENERATED_CABI_DIR}"` as a
  prior step, in the author's original code. The creation inside the tool
  was always redundant; removing it leaves a single source of truth instead
  of adding a second one. No custom `mkdir_p` was introduced because it is
  not necessary.
- Verified with `grep`: no remaining use of `std::filesystem` or `fs::` in
  the file (only mentions in explanatory comments).

Real execution verification, not just linking: the binary, invoked through
its stub (`build/tools/Debug/opus_cabi_tool.exe /tmp/cabi_exec_test`), exits
with `EXIT=0`, with no corruption either during execution or at process
shutdown, and writes **73 files** with real, correct content
(`open.hs` -> `#define cabiCABOPEN 268`, `about.hs` -> `#define cabiCABABOUT 1824`,
`print.hs` -> `#define cabiCABPRINT 1068`). The `std::filesystem` blocker is
closed.

### A NEW and different blocker: `.exe` suffix versus `$<TARGET_FILE:>`

With the tool now working, `ninja -C out/linux-winelib-debug
opus_generated_commands` **still fails, for a completely different reason**:

```

```

`winegcc`/`wineg++` emit the `opus_cabi_tool.exe` (POSIX stub) +
`opus_cabi_tool.exe.so` (real ELF) pair. CMake, which knows nothing of
winegcc's two-file convention, expands `$<TARGET_FILE:opus_cabi_tool>` (L367)
to the path **without** the suffix, which does not exist. Linking succeeds
and the tool works; what fails is only how the custom command names it.

`opus_mkcmd_tool`, `opus_mkdlg_tool`, `opus_bitapp_tool`, `opus_dibapp_tool`),
not just this one.

**No fix is applied here.** The two plausible options are (a) pin
`CMAKE_EXECUTABLE_SUFFIX` in the toolchain file, and (b) build the host
tools with native `gcc` instead of `winegcc`, which would produce
suffix-free ELF and remove the problem at the root. Option (b) **is exactly
the pending architecture decision about separating host tools from the
target**, which is explicitly reserved for the project owner. Stopping here
instead of improvising one of the two.

Note that these tools are generators that only ever need to run on the build
machine: there is no technical reason for them to go through Wine. That is
an argument for (b), but the decision is not made here.

## Separation of host tools from the Winelib toolchain (2026-08-09)

### Decision and rationale

Four of the five build tools move to compiling with native `gcc`/`g++`,
outside the Winelib toolchain. They are generators that only ever run on the
build machine: they read Opus sources and emit headers/initializers that the
engine later compiles. Compiling them with `winegcc` added nothing functional
and exposed them for free to the Winelib layer's failure modes (the same kind
of risk that had just been closed with `std::filesystem`).

Dependency audit, done by reading each tool's `#include`s before moving
anything:

| Tool | Source | Includes | Engine ABI |
|---|---|---|---|
| `opus_mkcmd_tool` | `OpusEtAl/tools/src/mkcmd.c` | `stdio, ctype, stdint, stdlib, string, vk.h, opus_host_compat.h` | no |
| `opus_mkdlg_tool` | `OpusEtAl/tools/src/mkdlg.c` | `stdio, ctype, opus_host_compat.h` | no |
| `opus_bitapp_tool` | `OpusEtAl/tools/src/bitapp.c` | `stdio, stdlib, string, bitapp.h` -> `stdint.h` | no |
| `opus_dibapp_tool` | `port/tools/opus_dibapp_tool.cpp` | `cstdint, fstream, iomanip, iostream, string, vector` | no |
| **`opus_cabi_tool`** | `port/tools/opus_cabi_tool.cpp` | `opus_x64_compat.h` -> `<windows.h>`, `sdm.h`, 73 `.hs` | **YES** |

Neither `vk.h`, `opus_host_compat.h`, nor `bitapp.h` pull in `<windows.h>`.

**Update 2026-09-01: a fifth native tool, `doc_inspector`.**
`port/tools/doc_inspector/doc_inspector.cpp` (`<algorithm> <cstdint>
<cstdlib> <cstring> <fstream> <iomanip> <iostream> <sstream> <string>
<vector>`, engine ABI: no) enters the same sub-project under the same
criterion of this audit. It is not a generator: it reads an already-saved
`.doc` and checks the FIB, FKP, and PLC from outside the engine. It knows the
on-disk layout by transcription from `Opus/filewin.c`, `Opus/wordtech/file.h`,
`fkp.h`, and `create.c`, it does not include any of them, which is what keeps
it out of `winegcc`. `opus_doc_inspector_test` consumes it; see §17 of
`03-word1-startup-blocked-behavior.md`.

### `opus_cabi_tool` does not move

Its output **is** the engine's ABI: it evaluates `sizeof` over the engine's
structures through `<windows.h>`, e.g.

```c
#define cabiCABOPEN Cabi((sizeof(CABOPEN) + sizeof(WORD) - 1) / sizeof(WORD), 1)
```

with `CABOPEN = { CABH cabh; WORD sab; CHAR **hszFile; int iDirectory; BOOL fReadOnly; }`.
Measuring it with a compiler other than the one compiling the engine is
exactly the error to avoid. Also confirmed that native `g++` does not even
compile it: `fatal error: excpt.h: No existe el fichero o el directorio`.

Grok Build finding, recorded as real but not conclusive evidence: compiling
it with native `g++` plus `-I/usr/include/wine/windows` gives the same
`sizeof`/macros, both in the samples and in the full dump of the 73 `.hs`
files. That is not enough to move it: that probe uses the same headers
`winegcc` consults, so it does not rule out something specific to the driver
(implicit flags, calling-convention model, `pragma pack` inherited from
headers not included in the minimal probe) affecting structures not sampled.
The ABI's correctness is not staked on someone remembering the right `-I`
instead of using the compiler designed for it.

### CMake mechanism chosen

`ExternalProject_Add` over a small, dedicated `CMakeLists.txt` at
`src/port/tools/host/`, configured with `-DCMAKE_C_COMPILER=gcc`
`-DCMAKE_CXX_COMPILER=g++` and **no** toolchain file, plus `IMPORTED GLOBAL`
targets with the same names in the main project. This way the existing 31
`$<TARGET_FILE:opus_*_tool>` references keep resolving untouched.

The one thing that does not survive is `DEPENDS`: ninja cannot resolve a
`DEPENDS` on the `IMPORTED_LOCATION` of an imported target (`missing and no
known rule to make it`, reproduced in a minimal project). `OPUS_<TOOL>_TOOL_DEP`
variables are introduced, holding the sub-build's name under Winelib and each
target's real name in all other cases, so the MSVC path keeps exactly the
same dependencies as before. The four original `add_executable` blocks stay
intact inside an `if(NOT OPUS_WINELIB_BUILD)`, so the Visual Studio build does
not change at all.

Verified: the four installed binaries are native ELF (`ELF 64-bit LSB
executable ... interpreter /lib64/ld-linux-x86-64.so.2`), with no `.exe`
stub, and the sub-build's `CMakeCache.txt` records `/usr/bin/gcc` and
`/usr/bin/g++`. Zero occurrences of `winegcc`/`wineg++` in its `build.ninja`.

### `.exe` suffix, fixed in the toolchain file

`CMAKE_EXECUTABLE_SUFFIX` ends up empty under this toolchain because
`CMAKE_SYSTEM_NAME` is not Windows and the build is treated as native Linux,
so `$<TARGET_FILE:>` was expanding to a nonexistent suffix-free path.
Reproduced with a minimal CMake target, nothing `cabi`-specific: it is a
toolchain property, not a per-target one. Fixed in
`src/cmake/toolchain-winelib.cmake` (`CMAKE_EXECUTABLE_SUFFIX`, `_C` and
`_CXX`), not per target or per custom command.

Side effect observed: with the suffix fixed, CMake's ABI detection now
reports "done" instead of failing. The forcing of `CMAKE_SIZEOF_VOID_P` was
not touched because of this, it may have become redundant, noted as a
possible future cleanup, not verified.

### Two Windows/Linux convention bugs found while unblocking the chain

1. **Relative path depth.** `src/CMakeLists.txt` passed MKCMD
   `-s../../../src/Opus/dlg/`, which assumes the Visual Studio preset's
   `binaryDir` (`out/`). With `out/<preset>/` there is one more level and it
   resolved to a nonexistent `out/src`, with the error
   `opuscmd.cmd:64: cannot open elx.txt file`. Replaced with
   `-s${CMAKE_CURRENT_SOURCE_DIR}/Opus/dlg/`, absolute and correct under
   either preset.

2. **BITAPP interprets `/` as a switch.** `bitapp.c:59` does
   `if (*(rgszArg[cCurArg]) == '/') SetFlag(...)`. On Windows absolute paths
   start with a drive letter, so it never collided; on Linux an absolute path
   **is** a leading `/`, and the tool answered `Invalid Switch on command
   line`. Fixed **at the caller**, not in the tool: the two
   `add_custom_command`s that invoke BITAPP now pass paths relative to the
   build directory via `file(RELATIVE_PATH)`. `OpusEtAl/` is left untouched.

### Method correction: the earlier error counts were understated

default**, and it is worth writing down so as not to fall into it again.
`ninja` defaults to `-k 1`: at the first failure it stops scheduling new
work. Since `opus_original_engine` has 331 steps, one early failure hides
everything that came after, and the resulting count measures *how far ninja
got*, not how many errors there are.

The correct numbers come from `ninja -k 0`, which continues until the graph
is exhausted. Comparison on the same tree:

| Measurement | Failed units | Errors |
|---|---|---|
| `ninja` (`-k 1`, default) | 1 | 1 |
| `ninja -k 0` | **43** | **182** |

The discrepancy was caught because `disp1.c` "disappeared" from the failure
list with nothing related having changed; forcing it to recompile in

### FARPROC calls by ordinal in CLIPBRD2.C (authorized, fixed)

	HDC, const BITMAPINFOHEADER *, DWORD, const void *,
	const BITMAPINFO *, UINT);
typedef int (WINAPI *OPUS_PFN_GETDIBITS)(
	HDC, HBITMAP, UINT, UINT, LPVOID, LPBITMAPINFO, UINT);

Guarded with `#if defined(__GNUC__) && !defined(_MSC_VER)`, as authorized.

it was first tried in the shared header and **it broke `CREATE2.C`**

### Family 1, `initializer element is not computable at load time` (90 errors)

All in `Opus/keys.h`, expanded from keyboard table macros into the `.c`
files that instantiate them (`iconbar3.c:710` is a typical expansion site).

Representative site, `Opus/keys.h:287`, expanded in `Opus/iconbar3.c:710`
inside `csconst KME rgKmeHdrIconBar[]`:

```c
#define rgKmeHdrIBDef \
	{ kcTab,	ktFunc, IBTab },		\
	{ kcReturn,	ktFunc, IBReturn    },		\
	...
```

With `KME` defined at `Opus/wordwin.h:451`:

```c
typedef struct _kme
	{
	unsigned kc : 12;
	unsigned kt : 3;
	union {
		int w;		/* generic */
		BCM bcm;	/* ktMacro */
		...
		PFN pfn;	/* ktFunc */
		...
		};
	} KME;
```

**What it actually is.** The C89 brace initializer with no designators
initializes **the union's first member**, which is `int w`. The `ktFunc` rows
put a function pointer there (`IBTab`, of type `void (*)()`). GCC says it in
two steps, and the first is the revealing diagnostic:

```
warning: initialization of 'int' from 'void (*)()' makes integer from
         pointer without a cast [-Wint-conversion]
note: (near initialization for 'rgKmeHdrIconBar[0].<anonymous>.w')
error: initializer element is not computable at load time
```

**Answer to the question posed: it is not deferred runtime initialization,
and it is not a compatibility guard.** The table is `csconst`, sorted by
`kc` for lookup, and consumed as constant data; it was always meant to be
load-time. What fails is the pointer's size: on Win16 a *near* function
pointer was 16 bits and fit in the union's integer member; on Win32 it was
32 bits and still fit in `int`, so MSVC accepted it as a load-time constant.
On x86-64 the pointer is 64 bits, does not fit in `int`, and the address
stops being a computable load-time constant for that member. It is therefore
**the same class of LP64/LLP64 defect that already broke `BITAPP` in Phase
1** (`bitapp.h:29`), not a syntactic variant.

**Homogeneity: total, verified, not estimated.** Of the 90 error-producing
lines in `keys.h`, **90 are `ktFunc` rows and 0 are `ktMacro` rows** (checked
by extracting every line number from the log and classifying it against the
source). The discriminating criterion is direct and cheap: **`ktMacro` rows
initialize the integer member with a `bcm`, which is an integer and does not
error; only `ktFunc` rows put in a function pointer.** That is, the family
is mechanical and single-pattern, and each row's own `kt` tag says which
group it belongs to with no need to look at anything else.

An MSVC extension (cast as lvalue) GCC never accepted. Same family as the

### `exp.c:1498`, STOPPED, it is a real (b), not an (a)

```c
	*((long *) pwArgs)++ = LWholeFromNum(&numT, TRUE);
```

Verified the consumer before touching anything, as requested. The chain is:

```c
	int  rgwArgs [celpMax];       /* exp.c:1427 */
	int *pwArgs = rgwArgs;        /* exp.c:1456 */
	...
	cwArgs = pwArgs - rgwArgs;    /* exp.c:1536 -- counts in units of int */
	lT = LPushMacroArgs(hpdkd->lppasproc, rgwArgs, cwArgs);
```

And the reader, in `port/original/opus_asm_misc.cpp:80`, **passes each `int`
of the array as an independent parameter**:

```cpp
template <std::size_t... Index>
long invoke_macro(void* procedure, const int* arguments,
                  std::index_sequence<Index...>) {
    using Procedure = long(__cdecl*)(std::conditional_t<true, int, ...>...);
    return reinterpret_cast<Procedure>(procedure)(arguments[Index]...);
}
```

That is: the reader **assumes one `int` slot per argument** and builds the
call signature from `cwArgs`. It does not reassemble a `long` from two
consecutive slots.

Consequence: historically (4-byte `long`) this write occupied **one** slot
and `cwArgs` grew by 1, so the macro-language procedure received one
parameter. Here `long` is 8 bytes: it occupies **two** slots, `cwArgs` grows
by 2, and the reader generates a call with **two `int` parameters** instead
of one. It compiles cleanly and breaks the call ABI.

**Not touched.** Simply moving the cast would swap the compile error for a
malformed call at runtime. The pending decision is whether the packing
should keep using 32-bit slots (in which case this write must split the
value, or the array must stop being `int`), or whether the reader should
learn per-argument widths.

### 2. `exp.c:1498` investigation, tree evidence (no execution)

#### What value arrives there

The site is **not** a generic interpreter path. It is inside the `switch
(dkt)` that packs arguments for an **external procedure call** (`sytDkd` /
DKD), right before `LPushMacroArgs(hpdkd->lppasproc, rgwArgs, cwArgs)`:

```c
case dktLong:
{
    extern long LWholeFromNum();
    NUM numT;
    BLTBH(&hpev->num, &numT, cbNUM);
    *((long *) pwArgs)++ = LWholeFromNum(&numT, TRUE);
}
```

Chain:

1. WordBasic's `Declare ... Lib "foo" ... (x As Long) ...` is parsed in
   `interp/main.c` (`DktFromElt(eltLong) -> dktLong`, ~1210-1213).
2. Without `As`, the name suffix decides: `$` -> string, `%` -> int,
   **default -> double**, **never** long. `dktLong` requires an explicit
   `As Long`.
3. `DeclDkd` does `LoadLibrary` + `GetProcAddress` and stores the `FARPROC`
   in `DKD.lppasproc` (`el.h:581`) and the types in `rgdkt[]` (`el.h:584`).
4. On the call, each arg resolves to `elvNum` when `dkt == dktLong`
   (`ElvFromDkt`: long and double -> `elvNum`), `hpev->num` is copied to
   `numT`, and `LWholeFromNum(&numT, TRUE)` extracts the integer part
   (truncating, not rounding).

**Value-type conclusion:** it is a **DLL interop integer** tagged WordBasic
`Long` / 32-bit Windows `LONG` in the original product, not an arbitrary
interpreter-heap integer. The EL's numeric payload is `NUM` (math pack
double); the cast to integer happens only at the Declare boundary.

#### Can it exceed 32 bits in real use?

Evidence from `LWholeFromNum` / `ourmath.h`:

- Function comment: if `*pnum` does not fit in `long`, the return is
  **undefined**; if `wExp > cDigLong` -> `MathError(fmerrOver)`.
- `#define cDigLong 10` with an explicit comment: *"A number of digits in
  0x7FFFFFFF"*, the digit ceiling was sized against the **maximum positive
  32-bit** value, not 64.
- Accumulation loop with `if (l < lPrev) goto lblOvrflw` (wraps at the
  platform's `long` width).

Implications:

| Platform | `long` | Behavior for large integers |
|---|---|---|
| Historical Win32 | 32 bit | Overflow -> MathError via wrap or `cDigLong` |
| Linux LP64 after widening | 64 bit | Up to 10 digits (~10^10) fit in `long` with no wrap; values between 2^31 and ~10^10 that **used to fail on Win32** can now **be returned** |

In real `As Long` usage toward Win16/Win32/Wine DLLs, the callee expects a
**32-bit LONG** on the stdcall/PASCAL stack. A value over 32 bits is not a
"legitimate macro result" at this boundary: it is a value the original
product rejected or truncated to the 32-bit `long` width. There is no table
in the tree of product Declares with documented `As Long` ranges; the
mechanism is 100% dynamic (user + `GetProcAddress`).

Other callers of `LWholeFromNum` (widening justified elsewhere):

| Site | Use |
|---|---|
| `elfile.c:1054` | file position (`DwSeekDw`), does benefit from >32 bit on LP64 |
| `elmisc.c:1800,1803` | time / tolerance |
| `elmisc.c:836` | MessageBox flags (low) |
| `elmisc2.c:412` | font point size (range 8-254) |
| `fieldpic.c:204` | inserts a number; the destination `CchInsertLongNfc` takes `LONG` |
| `fltexp.c:2715` | only the low bit (`& 1`) |
| **`exp.c:1498`** | **only** `dktLong` packing toward a DLL |

Globally re-narrowing `LWholeFromNum` to 32 bits would reintroduce the
problem in `elfile` and related code. The widening and this site **are not
the same contract**.

#### Reader side: are there `lppasproc` signatures?

- Declaration: `long (FAR PASCAL * lppasproc)();`, **no argument
  prototype**.
- Value: opaque `GetProcAddress`; **zero** static signature table in the
  tree.
- The only width metadata is at runtime: `DKD.rgdkt[i]` (`dktInt` /
  `dktLong` / `dktDouble` / `dktString`), up to `celpMax` (16) args.
- `LPushMacroArgs` / `invoke_macro` (`opus_asm_misc.cpp:80`) **ignore**
  `rgdkt`: they treat each `int` slot as an independent `int` parameter.
  They do not reassemble `long`s or pointers.

Historically on Win32, `long` == `int` == 32 bit -> one slot per `dktLong`
and the reader got it right by accident. On LP64, `long` = 8 B -> two slots
and the reader invents two `int`s.

### dktString, verdict

```c
lpstr = (LPSTR)*hsz;
*pwArgs++ = HIWORD(lpstr);  /* 16 bits */
*pwArgs++ = LOWORD(lpstr);  /* 16 bits */
```

- **Historical origin:** the Win16 far-pointer model, two words; on Win32
  flat, HIWORD/LOWORD of a 32-bit pointer still reconstruct the pointer if
  the callee reassembles with `MAKELONG`/`MAKELP`. On LP64 only 32 bits
  survive.
- **Public macros?** Yes: `Declare Function ... Lib "..." (s As String)` is
  user WordBasic toward external DLLs; also strings toward Word APIs exposed
  through the same DKD path.
- **Is there 64-bit handling in port?** `HIWORDX`/`LOWORDX` in
  `opus_x64_compat.h` are still **16-bit** halves of a `uintptr_t` (for
  packing points/messages), **not** a 32+32 hi/lo split for macro-arg
  pointers.
- **Blocks F4 (linking)?** No: the executable and its exports do not depend
  on this path.
- **Blocks real macro use with strings?** **Yes (runtime)**, whenever a DKD
  with `dktString` is invoked.
- **Not the same case as dktLong's (a'):** there the Windows contract is a
  32-bit LONG; here the value is a **pointer** and must survive 64 bits.

**Proposal (documented, not applied):**

1. Pack `uintptr_t p = (uintptr_t)lpstr` as two 32-bit `int`s (`(int)p`,
   `(int)(p>>32)`) in LE order, and extend `LPushMacroArgs`/`invoke_macro`
   to reassemble pointers when `rgdkt[i]==dktString` (F3's (b) option,
   extended).
2. Port-only alternative: a packing API in `opus_asm_misc.cpp` with a
   width-by-`DKT` table.
3. Do not reuse 16-bit HIWORD/LOWORD.

### Sites critical for manual review (F5+)

## Grok Build session #5b, dktString 64-bit implemented (2026-08-09)

Phase 6 precondition. No commit.

### Problem

`exp.c` packed `LPSTR` for `Declare ... As String` with:

```c
*pwArgs++ = HIWORD(lpstr);
*pwArgs++ = LOWORD(lpstr);
```

Only 32 bits of the pointer (16+16). On LP64 the heap lives outside that
range.

### Design applied

1. **Writer** (`exp.c`, guarded `__GNUC__ && !_MSC_VER`):
   - `uintptr_t up = (uintptr_t)(void *)lpstr`
   - two `int` slots: lo32, hi32
2. **Reader** (`port/original/opus_asm_misc.cpp`):
   - New API `LPushMacroArgsTyped(proc, args, cwArgs, dkts, dkt_count)`
   - With `dkts == NULL`: legacy behavior (one `int` slot -> one arg)
   - With types: for each `dktString` it reassembles a `void*` from
     lo|hi<<32 and passes **one** pointer argument; `dktInt`/`dktLong` -> one
     GPR; `dktDouble` -> a 64-bit payload in a GPR (bit pattern; XMM float
     stays a debt)
3. **Call site** (`exp.c`):
   `LPushMacroArgsTyped(..., (const unsigned char *)hpdkd->rgdkt, idktMacParam)`
4. Declaration in `opus_x64_compat.h`; stub in `opus_original_plc_test.c`.
5. MSVC branch: unchanged (HIWORD/LOWORD + untyped `LPushMacroArgs`).

6 compile errors. The link step never runs because the target's single
translation unit fails and `ninja` stops, unable to continue.

**Root cause:** `opus_word1_ui_test.cpp` is C++20, depending on WORD1. It
uses two MSVC CRT APIs that do not resolve in Winelib's glibc mode:

- **`_wcsicmp`** (lines 91, 111, 160): case-insensitive wide-string
  comparison from the MSVC CRT. The POSIX alternative is `wcscasecmp`; it is
  not declared in Wine's headers in glibc mode.
- **`min(LONG, long int)`** (lines 170, 379, 380): `NOMINMAX` suppresses
  `<windows.h>`'s `min`/`max` macros, leaving `<algorithm>`'s `std::min<>`,
  which requires identical types for template deduction. `LONG` maps to
  `int` (32 bits) in Wine's headers; `long int` is 64 bits on Linux LP64.
  Under MSVC (LLP64), `long` == `int` == 32 bits and the deduction resolves
  with no error.

**Explicit distinction from Gap 1 (the four `_test` targets):**

This is **not** the same problem. Gap 1's four targets are C (`Opus/*.c`)
that fail because they compile without the
`-std=gnu89 -funsigned-char -fms-extensions -fpermissive` flags.
`opus_word1_ui_test` is C++20 (`target_compile_features(... PRIVATE
cxx_std_20)`), those flags do not apply and would not fix the problem. Gap
2 has two independent causes: the absence of `_wcsicmp` (an MSVC CRT symbol
not exposed in glibc mode) and the `LONG` / `long int` type mismatch in
`min<>`, caused by the combination of `NOMINMAX` and the LP64/LLP64
divergence of `long`. Different problems, in a different target, with
different root causes.

**Scope:** does not block `opus_original_engine` or `WORD1`. The dependency
in `CMakeLists.txt:1480` runs the other way: `opus_word1_ui_test` depends on
`WORD1`, not the reverse. Without a fix, the eight test variants that launch
`WORD1` through this executable (`opus_word1_ui_test`,
`opus_word1_clipboard_shortcut_test`, `opus_word1_typing_test`,
`opus_word1_interaction_test`, `opus_word1_selection_test`,
`opus_word1_font_typing_test`, `opus_word1_about_test`,
`opus_word1_save_as_test`) do not compile under Winelib. The engine and the
main executable are unaffected.
